# Этап 3 — Сборка сайта по итоговому дизайну

Вход: артефакт Claude Design из `state.json` → `design_artifact_url` (уже доработанный командой), бриф, контент, ассеты. Выход: полный Astro-проект, который собирается без ошибок, `DEPLOY.md`, `stage: "built"`.

Перед началом прочитай `references/design-craft.md`, `references/anti-ai.md`, `references/astro-stack.md` и `references/seo.md`.

## 0. Context7

Выполни проверку из `SKILL.md` → «Context7 — обязательное условие для кода». Не прошла — остановись: дизайн читать можно, код писать нельзя.

**Node.js.** Проверь `node --version`. Если команды нет:
- в Windows поищи установленный, но не попавший в PATH Node: `/c/Program Files/nodejs`. Нашёлся — добавляй его в PATH в каждой команде: `export PATH="/c/Program Files/nodejs:$PATH"`;
- не нашёлся — предложи пользователю установку и дождись согласия: `winget install --id OpenJS.NodeJS.LTS -e --accept-source-agreements --accept-package-agreements` (macOS: `brew install node`). Без Node сборки не будет.

## 1. Прочитать итоговый дизайн

1. `Artifact` → `action: "read"`, `url` из `state.json`. Это **последняя** версия: команда правила её в Claude Design, и именно она теперь источник истины, а не первоначальный макет и не `.webik/design.md`.
2. Если ответ называет локальный файл с полной страницей, читай его. Посмотри список файлов артефакта (`action: "list"`, `scope: "files"`, тот же `url`) и прочитай файлы артбордов и данных (`action: "read"`, `paths`).
3. Если ссылки в `state.json` нет, спроси её у пользователя. Не собирай сайт по памяти о макете.

## 2. Сверить с исходным макетом

Сравни прочитанное с `.webik/design.md` и составь короткий список изменений, внесённых командой: цвета, шрифты, размеры, порядок и состав секций, удалённые и добавленные блоки, правки текстов.

- Правки команды важнее твоих исходных решений. Ничего не «возвращай как было».
- Обнови `.webik/design.md`: новые токены и строка в таблице решений «изменено в Claude Design».
- Если правка противоречит правилам (выдуманный отзыв, удалённый обязательный чекбокс согласия, контраст текста ниже 4.5:1), сделай как в дизайне, но вынеси пункт в итоговый отчёт как вопрос. Не исправляй молча.
- Если в дизайне есть то, что нельзя однозначно сделать в коде (непонятно поведение блока, нет мобильной версии секции), прими разумное решение в духе дизайна и тоже упомяни его в отчёте.

## 3. Каркас проекта

Если Astro-проекта ещё нет, создай его по `references/astro-stack.md` → «Создание проекта», предварительно сверив установку и конфиги с документацией через Context7. Если есть (повторная сборка), не пересоздавай, а обновляй.

## 4. Дизайн-система в коде

1. Токены из дизайна → `src/styles/global.css` (`@theme` Tailwind). Имена токенов по смыслу, не `gray-700`.
2. **Шкала типографики — тоже токены** (`--text-display`, `--text-h1`, `--text-h2`, `--text-h3`, `--text-body`, `--text-small` с парными line-height), см. `references/astro-stack.md` → «Шкала типографики». В разметке только `text-h2` и т. п.; произвольные `text-[1.375rem]` запрещены. Нужен новый размер — добавь токен и запиши решение в `design.md`. На «Аквамарине» без этого у H2 оказалось 11 разных размеров.
3. Шрифты — локально, через `@fontsource`/`@fontsource-variable`, не через Google Fonts.
4. Базовые компоненты: `Button`, `Container`, `Section`, `Heading`, поля форм. Они повторяют состояния с артборда «Состояния». Повторяющуюся кнопку не копируй разметкой: только `<Button variant="…">`.

## 5. Шаблоны и страницы

1. Общий макет: `BaseLayout.astro` с SEO-компонентом, `Header`, `Footer`, мобильное меню (доступное: кнопка с `aria-expanded`, закрытие по Escape, фокус).
2. Каждую секцию из артбордов — отдельным компонентом в `src/components/sections/`.
3. Шаблон каждого типа страницы собирается из секций **точно по артборду**: порядок, отступы, размеры, иерархия. Desktop и mobile — по своим артбордам, промежуточные ширины (768, 1024) должны выглядеть аккуратно.
4. Затем — **все страницы** из карты страниц брифа, а не только образцы. Каждая страница берёт свой контент из `.webik/content/` и раскладывается по шаблону своего типа. Однотипные страницы (услуги, статьи, товары) — через content collections (`src/content/`), а не копированием `.astro`-файлов.
5. **Тексты — все, а не только заголовки.** Смысл и факты из `.webik/content/`, форма по правилам `references/seo.md` → «Тексты» и `references/anti-ai.md`. Переписываются **все текстовые блоки каждой страницы**: H1, лид, основной текст, списки («что входит», «что взять»), подписи, FAQ, тексты кнопок. Перенести тело страницы как есть со старого сайта и переписать только шапку — ошибка: на «Аквамарине» ревью поставило за это блокер (35 из 36 туров со старыми текстами, 78 «!», дефисы вместо тире, цены «8.000 руб.»).
   - Типографика по всему контенту: тире «—» вместо дефиса между словами, цены «8 000 ₽», без «!», без капса, «ёлочки», неразрывные пробелы.
   - Механическую чистку (типографику) можно делать скриптом, но смысловую редактуру — только читая каждый текст. Образец — первая отредактированная страница каждого типа.
   - Если команда правила текст в Claude Design, берётся её вариант.
6. Изображения: из `.webik/source/assets/` → `src/assets/` (переименуй по смыслу: `remont-kvartiry-kuhnya.jpg`), вывод через `<Image>`/`<Picture>` из `astro:assets`, с осмысленным alt.
7. **Возможности webik.** Интерактивные блоки из макета и брифа (галерея, фильтр каталога, калькулятор, квиз, запись и т. п.) — по `references/features.md`: сначала готовый компонент из `templates/features/` плагина, затем порт из исходников webik.tech. Данные — только реальные данные клиента.

## 6. SEO и техническое

Всё из `references/seo.md`: метаданные каждой страницы, микроразметка, sitemap, robots, канонические адреса, 404, редиректы по карте URL. Формы — по `references/astro-stack.md` → «Формы».

## 7. Проверка

1. `npm run build` проходит без ошибок и предупреждений о сломанных изображениях.
2. `npm run preview` и визуальная проверка, если есть браузерный инструмент (Claude in Chrome, встроенный браузер): главная и по одной странице каждого типа, ширины 1440 и 390. Сравни с артбордами. Ищи: наложения, горизонтальный скролл, пустые блоки, отсутствующие картинки, нечитаемый текст, отличия от дизайна.
3. Проверка собранного HTML скриптом, всегда, с браузером или без:
   ```bash
   node "<папка скилла>/scripts/check-site.mjs" dist --urlmap .webik/brief.md --redirects deploy/redirects.nginx.conf
   ```
   Он проверяет: уникальные `<title>` и description, ровно одну `<h1>`, битые внутренние ссылки и картинки, alt, `lang`, canonical, оставшиеся заглушки `[НУЖНО ОТ ВАС]` (это предупреждение, не ошибка) и что каждый старый URL из карты страниц либо существует, либо есть в редиректах. Ошибок быть не должно. Свой скрипт проверки для этого не пиши.
4. Признаки AI-работы: `bash "<папка скилла>/scripts/check-ai-tells.sh" src`. Каждое срабатывание исправь; настоящий элемент клиента (зарегистрированный слоган, фирменный шрифт) пометь `webik-allow` с причиной и запиши в `design.md`. Скрипт должен завершиться без находок. Затем вручную пройди то, что скрипт не видит (`references/anti-ai.md` → «Проверка», п. 3): штампы в новых формулировках, композицию, сверку каждой цифры и каждого факта с `.webik/content/`.
5. Быстрая самопроверка по `design-craft.md` → «Проверки». Для полного ревью предложи `/webik:design-review`.

## 8. Подготовка к выкладке

Создай в корне проекта `DEPLOY.md` по `references/deploy.md` → «Прод». Запиши группы «проблема → что сделано» в `src/data/compare.ts` по `references/compare.md` → «Список проблем и исправлений». Обнови `state.json`: `stage: "built"`.

Коротко:

- результат сборки и проверки;
- следующий шаг: `/webik:demo`, чтобы выложить на демо.
